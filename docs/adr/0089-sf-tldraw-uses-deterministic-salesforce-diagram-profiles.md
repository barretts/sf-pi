# SF tldraw uses deterministic Salesforce diagram profiles

Status: accepted

SF tldraw will keep one `tldraw_canvas` family tool and add three Salesforce-specific rendering actions: `render_salesforce_data_model`, `render_salesforce_architecture`, and `render_salesforce_sequence`. Each action accepts a typed, versioned **Salesforce Diagram Spec** and applies a distinct **Salesforce Diagram Profile**; raw canvas execution remains an escape hatch rather than the normal Salesforce diagram path. When the local canvas is ready, **Salesforce Diagram Routing** prefers these actions for Salesforce diagram requests unless the user explicitly requests Mermaid, text, or another format; unavailable canvas state is reported before offering a fallback. This preserves a small Pi tool surface while making Salesforce output repeatable, testable, and independent of Mermaid constraints.

Every spec declares its **Diagram Grounding** as either `reference` or `org`. Reference-grounded workflows use official Salesforce documentation. Org-grounded workflows name an explicit authenticated org and gather schema, relationships, counts, OWD, and optional scale evidence through the existing SF Pi capability owners before rendering. Ambiguous requests ask the user to choose grounding rather than silently using an available org. Org diagrams show only a user-approved display label, org type, and observation time; private org IDs, usernames, instance URLs, and auth details stay off-canvas. Broad count enrichment uses approximate org counts by default, with exact user-visible counts opt-in. The renderer never guesses missing Salesforce facts.

Every diagram uses a compact title, one-sentence scope, grounding/as-of metadata, and a legend only when direct labels are insufficient. Data Model diagrams use pale full-card fills for Standard, Custom, and External families, org-resolved icon-tile colors, logical names, and physical API names in parentheses directly beneath the measured label bounds with an 8-unit vertical gap and no `API` prefix. Relationship field names appear only to disambiguate. Cardinality uses integrated vector endpoints—bar for one, crow's foot for many, and optionality circles in full mode—never tiny `1/N` text shapes. Marker anchors are computed from tldraw's clipped page-space connector terminals and local tangent, not from assumed card centers. Placement solves the marker's local anchor through tldraw's actual origin-based shape transform, and verification resolves that anchor back with `getShapePageTransform(marker).applyToPoint(...)`; hand-rolled center-rotation math is prohibited. Anchor-to-terminal distance must be at most one canvas unit for horizontal, reversed, and vertical fixtures, and placement is recomputed after render, relayout, and update. Markers sit exactly on the card boundary, visually merge with the relationship axis without an opaque decoration background, and share its direction; aligned objects use straight connectors and elbow routing is reserved for real obstacle avoidance. Relationship type remains a compact `LK` or `MD` pill centered at the connector's actual midpoint. Official icon glyphs remain high-contrast on vivid org/SLDS color tiles instead of inheriting muted tldraw theme fills. Observation pills use solid semantic fills and fixed anchors: LDV floats over the top-right card edge and OWD floats over the bottom-center edge. Special families such as Big Objects, Platform Events, Custom Metadata, Custom Settings, and managed-package objects use badges and icons instead of additional fill colors. LDV is a configurable policy signal with a default threshold of two million records; measured skew and query risk remain optional observations. OWD is compressed into a header default plus exception pills. Record types are hidden by default and appear only when explicitly requested. Overview cards are the default; a bounded Key Fields view is optional and full field dumps are excluded. Initial graph layout adds 20–30% whitespace beyond the minimum card/connector fit so compactness never forces label or endpoint collisions.

System/Solution Architecture diagrams use neutral cards, approved official product marks or semantic icon fallbacks, one concise responsibility, ownership badges, and three connector meanings: solid directional flow, dashed asynchronous or batch flow, and thin undirected dependency. Connector labels are required, and separate directional interactions remain separate edges. External systems use neutral semantic icons unless the spec supplies an explicitly approved logo asset. Interaction/Sequence diagrams use fixed lanes and remain static by default. **Step-Through Presentation** is source-gated until the runtime can compose Previous, Next, and Reset behavior without overwriting an existing document script; it never autoplays or silently replaces a user script.

The initial renderer uses Dagre for graph-family placement and fixed layout for sequence diagrams. SF tldraw probes a machine-readable `GET /api/capabilities` contract when the runtime provides one and otherwise uses only the verified Canvas API v1 route set. The currently verified runtime exposes neither that endpoint nor native document creation, so no-open-document state returns an open-board recovery path. A future advertised create operation remains capability-gated; SF tldraw never falls back to OS keystrokes or direct `.tldraw` archive generation. A new render creates a named page by default. Explicit update mode refreshes **Profile-Managed Diagram Elements** while preserving human placement and user-created annotations; relayout and replace are separate explicit modes. Specs that exceed the profile's readability budget require an explicit multi-page scope rather than automatic splitting or shrink-to-fit. A render is complete only at **Salesforce Diagram Readiness**: valid spec, no text overflow or overlap, and no unbound semantic connectors. Asset or evidence fallbacks remain visible warnings. Successful renders return one thumbnail and the full image path.

SF tldraw will depend on a pinned `@salesforce-ux/design-system` release for all five SLDS icon categories; this package is accepted by the repository's production BSD-3-Clause license policy. Used, unchanged icons are embedded into the `.tldraw` document for portability and retain upstream license attribution. Org theme metadata is authoritative for org-grounded object icons and icon-tile color. Reference-grounded custom objects use a generic custom-object icon unless the spec declares an explicit presentation override. A curated v1 registry covers Salesforce Platform, Sales Cloud, Service Cloud, Experience Cloud, Marketing Cloud, Commerce Cloud, Data 360, Agentforce, MuleSoft, Tableau, and Slack product marks. Product marks enter the registry only from an official downloadable source, remain unmodified, carry provenance and attribution, and fall back when an approved asset is unavailable.

The Manager settings surface is intentionally limited to four inherited scalar preferences: Cardinality Presentation (`simplified` by default or full physical optionality), LDV threshold (`1M`, `2M`, `5M`, or `10M`; default `2M`), record-type presentation (`off` by default, with `auto` or `always` available), and interaction presentation (`static` by default or step-through). Font, palette, icon provenance, card grammar, and connector grammar are profile standards rather than customization knobs.

The renderer must prove these profile invariants through deterministic fixture specs and visual regression evidence. A fixture is rendered in one action and asserts: zero tldraw lints; parenthesized API names with an 8-unit measured gap; cardinality and relationship-pill anchors within one unit of actual clipped connector geometry; fixed LDV/OWD pill anchors; vivid icon glyphs above their color tiles; at least the profile spacing budget; and no record-type, renderer-error, or text-cardinality artifacts by default. A fixture that violates any assertion cannot satisfy **Salesforce Diagram Readiness**.
